# Бот для заказов: пюре и сиропы

Версия 0.1.1, подготовлена 7 ноября 2026 года. Код и локальные проверки готовы. К реальному Telegram и Cloudflare проект пока не подключён: для запуска нужны настройки клиентского аккаунта, рабочей группы и секреты.

В `ADMIN_IDS` уже указаны два аккаунта владельца: `9212424642` и `8554261748`. Оба получают уведомления и могут управлять паузой диалогов. Это не ID группы менеджеров. `OWNER_ID` пока пуст: сюда нужно вписать ID именно того аккаунта, в который приходят заказы и к которому подключается бот. Выбирать первый административный ID автоматически проект не будет.

## Быстрый запуск из GitHub через Cloudflare

Код находится в [usahelauri/manager42](https://github.com/usahelauri/manager42).

1. В Cloudflare открыть **Workers & Pages → Create application → Import a repository** и выбрать этот репозиторий. Создавать **Worker**, не Pages.
2. Указать имя Worker **telegram-order-manager** — оно должно совпадать с `name` в `wrangler.jsonc`. Production branch: `main`; root directory: `/`; build command: `npm test`; deploy command: `npx wrangler deploy`. Зависимости устанавливает система сборки.
3. После первого размещения открыть Worker → **Settings → Variables and Secrets** и добавить именно runtime secrets `BOT_TOKEN` и `WEBHOOK_SECRET`. Не сохранять токен Telegram в исходниках и не путать runtime secrets с переменными сборки.
4. Зарегистрировать Telegram webhook по шагу 2 ниже. Адрес — опубликованный HTTPS URL Worker с окончанием `/telegram`. Секрет в регистрации должен совпадать с runtime `WEBHOOK_SECRET`.
5. Нажать «Старт» в боте с обоих административных аккаунтов. Получить `/id` в группе менеджеров. Указать `OWNER_ID`, `MANAGERS_CHAT_ID` и при необходимости `MANAGERS_THREAD_ID` в `wrangler.jsonc`, затем сохранить изменения в GitHub. Автоматическая сборка применит настройки.
6. Подключить бота в настройках Telegram аккаунта, принимающего заказы, разрешив ответы и доступ сначала к одному тестовому диалогу. Выполнить проверку из раздела «Проверка перед клиентами».

При этом варианте Cloudflare самостоятельно получает код из GitHub; секреты `CLOUDFLARE_API_TOKEN` и `CLOUDFLARE_ACCOUNT_ID` в GitHub не нужны. Альтернативный GitHub Actions workflow публикации по умолчанию пропускается: его можно включить переменной репозитория `CLOUDFLARE_DEPLOY_ENABLED=true` после настройки соответствующих secrets. Не включать оба способа автоматической публикации одновременно.

## Что уже реализовано

- Официальное подключение к личному аккаунту Telegram через Business/Secretary Mode. Без авторизации по номеру телефона, API ID/Hash и пользовательской сессии.
- Сбор нескольких входящих сообщений одного клиента: 30 секунд тишины, максимум 120 секунд ожидания.
- Заказ с известным товаром и количеством копируется в рабочую группу: исходные тексты, форматирование, фото, видео, документы и аудиофайлы. Имя, username и ссылка на отправителя не добавляются. Контакт, уже написанный внутри самого заказа, остаётся.
- После подтверждённой отправки всех частей заказа клиенту приходит «Здравствуйте, принял.».
- Вопрос, неизвестный формат и голосовое сообщение: просьба подождать, уведомление владельцу, пауза автоматизации в диалоге. Вложения по возможности направляются владельцу для проверки.
- Менеджеры отвечают **реплаем на сообщение заказа**. «Нет в наличии», вопросы и прочие нестандартные ответы вызывают уведомление владельцу и просьбу подождать в рабочей группе и у клиента. Короткие подтверждения вроде «ок» и «оформлен» игнорируются.
- Собственное сообщение владельца в диалоге ставит автоматизацию на паузу. Возврат — явной командой `/resume ID_КЛИЕНТА` в личном чате бота.
- Повторы Telegram отсекаются. Состояние и связь «сообщение менеджерам → клиент» сохраняются между перезапусками.
- Изменение или удаление уже переданного заказа вызывает уведомление владельцу. До отправки правки меняют ожидающий пакет, удаление убирает сообщение из него.
- Уведомления, вложения для проверки и сообщения о подключении отправляются в оба административных аккаунта. Ошибка доставки одному не мешает другому. Подтверждённые доставки не повторяются при ограничении частоты у второго получателя; сбои видны в `/status`.

## Что прислать для настройки

1. Ссылку на созданный GitHub-репозиторий. Если он закрытый, подключённый GitHub должен иметь к нему доступ.
2. Публичное имя созданного бота: `@имя_бота`.
3. 3–5 типичных заказов, включая многострочные и несколько сообщений подряд. Личные контакты в примерах можно заменить.
4. 2–3 примера вопросов клиентов и ответов менеджеров, при которых нужно подключить владельца.
5. Указать, какой аккаунт принимает клиентские заказы (`OWNER_ID`). После первоначального развёртывания — ID рабочей группы из команды `/id`. Если группа с темами, нужен также ID темы; команда показывает его, если отправлена внутри темы. Два административных ID уже настроены.
6. При необходимости — другой текст подтверждения или ожидания. По умолчанию используются согласованные короткие ответы.

Токен бота, Cloudflare API Token, пароли и коды входа **не отправляются в чат и не записываются в репозиторий**. Токен BotFather сохраняется в секрете `BOT_TOKEN` у Worker. Telegram API ID/API Hash и ключ нейросети для этой версии не нужны.

## Шаг 1. Создать бота и аккаунт размещения

1. В [@BotFather](https://t.me/BotFather) выполнить `/newbot`, выбрать имя и username. Сохранить токен у себя.
2. В настройках этого бота включить **Secretary Mode**. В некоторых интерфейсах и старых материалах это называется Business Mode.
3. Создать аккаунт [Cloudflare](https://dash.cloudflare.com/sign-up). Проект использует Workers и SQLite-backed Durable Objects, доступные на Free в пределах квот. Биллинг платного тарифа автоматически проект не включает.
4. Выбрать существующую рабочую **группу**, добавить в неё этого бота и разрешить отправку сообщений и необходимых вложений. Администраторские права для базового сценария не нужны. Privacy Mode можно оставить включённым: ответы реплаем на сообщения самого бота доступны и при нём. Ответы без реплая проект не связывает с заказом.

## Шаг 2. Первое размещение

Нужен Node.js 22 или новее. Из папки проекта:

```bash
npm install
npm test
npx wrangler login
npm run deploy
```

Пока `OWNER_ID` и `MANAGERS_CHAT_ID` пусты, автоматизация заказов отключена, но команда `/id` доступна.

Добавить секреты в Cloudflare — команды запросят значения без записи в исходный код:

```bash
npx wrangler secret put BOT_TOKEN
npx wrangler secret put WEBHOOK_SECRET
```

Для `WEBHOOK_SECRET` можно сгенерировать 32 случайных байта:

```bash
node -e "process.stdout.write(require('node:crypto').randomBytes(32).toString('hex'))"
```

Сохранить одно и то же значение в секрете Worker и локальном `.dev.vars`, чтобы оно совпало при регистрации webhook.

Скопировать `.dev.vars.example` в `.dev.vars`, заполнить `BOT_TOKEN`, `WEBHOOK_SECRET` и `WEBHOOK_URL`. Последний — адрес развёрнутого Worker с окончанием `/telegram`. Файл `.dev.vars` исключён из Git. Затем:

```bash
npm run telegram:webhook
npm run telegram:check
```

Скрипт регистрации не удаляет накопившиеся обновления Telegram. В запросах не передаёт токен через аргументы командной строки. Значения токена не печатает.

## Шаг 3. Узнать ID и подключить аккаунт

1. Открыть бота **с каждого из двух административных аккаунтов** и нажать «Старт»: бот не может первым начать с ними личную переписку. Затем с аккаунта, в который приходят клиентские заказы, отправить `/id` и записать «Ваш ID» в `OWNER_ID` файла `wrangler.jsonc`. `ADMIN_IDS` оставить как настроено. Административные команды доступны ещё до заполнения `OWNER_ID`.
2. Написать `/id` в рабочей группе. Записать «ID чата» в `MANAGERS_CHAT_ID`. Он обычно отрицательный. При работе внутри темы записать «ID темы» в `MANAGERS_THREAD_ID`.
3. Повторить `npm run deploy`.
4. В настройках подключения ботов своего Telegram выбрать этого бота. Разрешить доступ к нужным клиентским диалогам и ответы от имени аккаунта. Личные и рабочие диалоги, которые не нужно автоматизировать, исключить в Telegram. Для базовой логики достаточно возможности отвечать; доступ к подаркам, платежам и редактированию профиля не нужен.
5. Если бот был подключён до заполнения ID, переподключить его, чтобы получить свежие сведения о подключении. Написать ему `/status`.

Сам `business_connection_id` приходит от Telegram автоматически. Искать и присылать его вручную не нужно. По актуальной документации подключённые боты доступны также пользователям без Premium; приложение должно поддерживать эту настройку.

## Шаг 4. Обновления из GitHub

В проект включены два GitHub Actions workflow:

- `ci.yml`: проверки кода при push и pull request;
- `deploy.yml`: проверки и размещение в Cloudflare при push в `main` или ручном запуске.

GitHub хранит код и запускает обновление. Сообщения круглосуточно принимает Worker в Cloudflare; отдельного постоянно работающего GitHub Actions процесса нет.

В GitHub → Settings → Secrets and variables → Actions создать:

| Название секрета GitHub | Что сохранить |
|---|---|
| `CLOUDFLARE_API_TOKEN` | Ограниченный токен Cloudflare для публикации Worker и Durable Objects в выбранном аккаунте |
| `CLOUDFLARE_ACCOUNT_ID` | ID аккаунта Cloudflare |

Удобно начать с шаблона Cloudflare API Token «Edit Cloudflare Workers», ограничив его нужным аккаунтом и проверив права для Durable Objects. Конкретные разрешения показываются в текущем интерфейсе Cloudflare. Не выдавать Global API Key.

`BOT_TOKEN` и `WEBHOOK_SECRET` остаются **секретами самого Worker**. GitHub workflow их не читает и не выводит. Первоначальное создание и последующее обновление конфигурации не требуют переносить токен Telegram в GitHub. После добавления двух Cloudflare secrets включить workflow переменной репозитория `CLOUDFLARE_DEPLOY_ENABLED=true` в Settings → Secrets and variables → Actions → Variables. Пока переменная не включена, публикация пропускается.

## Настройки и управление

| Переменная | Назначение |
|---|---|
| `OWNER_ID` | Единственный аккаунт, к которому подключён бот для клиентских переписок; не заменяет список администраторов |
| `ADMIN_IDS` | ID администраторов через запятую: оба управляют ботом в личном чате и получают уведомления. Если переменная отсутствует, для совместимости используется `OWNER_ID` |
| `MANAGERS_CHAT_ID` | Единственная рабочая группа назначения |
| `MANAGERS_THREAD_ID` | Необязательная тема в рабочей группе |
| `DEBOUNCE_SECONDS` | Сколько секунд тишины ждать перед обработкой |
| `MAX_BATCH_SECONDS` | Максимальное ожидание при непрерывной переписке |
| `PRODUCT_WORDS` | Названия товаров для первичного распознавания, через запятую |
| `ACCEPT_TEXT` | Подтверждение получения заказа |
| `WAIT_TEXT` | Просьба клиенту подождать |
| `MANAGER_WAIT_TEXT` | Ответ в рабочей группе при вопросе менеджеров |
| `RETENTION_DAYS` | Хранение служебных копий и связей заказов, по умолчанию 30 дней |

В личном чате с ботом с любого из двух административных аккаунтов:

```text
/id
/status
/pause 123456789
/resume 123456789
```

Уведомление владельцу включает ID клиента и ссылку на его профиль. Для клиентов без username ссылка на профиль может зависеть от клиента Telegram и настроек приватности; ID всегда остаётся в уведомлении. В группу менеджеров эти данные не добавляются.

Ответ на `/status`, `/pause` или `/resume` приходит только в тот административный чат, из которого отправлена команда. Посторонние аккаунты и команды из групп не получают административного доступа. Разрешение управлять ботом не разрешает подключение к другому клиентскому аккаунту: для этого проверяется отдельный `OWNER_ID`.

Пауза действует до `/resume`. Возобновление обрабатывает **новые** входящие сообщения и не отправляет старые заказы заново. Через 30 дней старые данные и связи удаляются постепенно; минимальное состояние приостановленного диалога сохраняется, чтобы пауза не закончилась сама. Удаление служебных данных не удаляет сообщения в самих чатах Telegram.

## Ограничения первой версии

- Распознавание работает по консервативным правилам, без нейросети. Оно требует названия известного товара и количества, а вопросы и неизвестные форматы отправляет владельцу. До подключения всех клиентов нужно адаптировать словарь и правила к реальным примерам. Ключ нейросети не требуется.
- Голосовые, контакты, геолокации, защищённый контент и неподдерживаемые новые типы сообщений не оформляются как обычный заказ. Бот уведомляет владельца. Он не расшифровывает голос и не читает текст внутри фотографий или таблиц.
- Альбомы и серии сообщений копируются отдельными сообщениями, без метки пересылки и без добавления сведений об отправителе. Все части одного заказа хранят одну внутреннюю связь с клиентом.
- Если человек присылает только картинку без текста заказа, бот передаёт вопрос владельцу. Если часть заказа приходит после окна сборки, она рассматривается отдельно.
- Telegram разрешает ответы от подключённого бота только в подходящих личных чатах, где клиент писал в последние 24 часа. Если окно истекло или права сняты, бот сообщает владельцу, что клиенту не удалось ответить. Он не заявляет, что отправил автоответ, когда Telegram его не принял.
- При явном ограничении частоты (`429`) отправка переносится, уже подтверждённые части повторно не посылаются. При обрыве связи, ответе `5xx` или перезапуске между отправкой и подтверждением результат может быть неизвестен. Такой заказ ставится на ручную проверку: обещать абсолютное отсутствие дублей у внешнего Telegram API нельзя.
- Это последовательный обработчик для небольшого потока заказов одного владельца. Длительное ограничение Telegram может задержать следующие сообщения. Перед масштабированием понадобится разнести очереди.
- Workers, Durable Objects и GitHub Actions имеют квоты. Работа в России зависит от доступности Cloudflare; сама возможность регистрации не гарантирует доступность у конкретного провайдера. Надёжность реального webhook проверяется тестовыми сообщениями после развёртывания.
- `/health` проверяет доступность HTTP-обработчика, а не факт подключения Telegram или готовность всей автоматизации. Для настройки использовать также `telegram:check`, `/status` и контрольный заказ.

## Проверка перед клиентами

1. Временно разрешить боту только один тестовый личный диалог.
2. Отправить текстовый заказ, затем заказ из нескольких сообщений и заказ с фото. Проверить исходное содержание в группе и одно подтверждение клиенту.
3. С двух тестовых аккаунтов отправить одинаковые заказы. Менеджером ответить «Нет в наличии» на один из них. Уведомление и ожидание должны относиться только к нужному клиенту.
4. Написать клиенту вручную и убедиться, что автоматические ответы остановились. Затем проверить `/resume`.
5. Проверить изменение и удаление сообщения заказа, отсутствие прав на отправку в группу и отключение подключения к аккаунту.
6. Проверить уведомления в обоих административных аккаунтах и команды `/status`, `/pause`, `/resume` с каждого из них.

Автоматические тесты используют локальную модель хранилища и имитацию Telegram API. Они не заменяют эти контрольные отправки в реальном аккаунте. До такой проверки не подключать сразу всех клиентов.
